# Как передавать задачи Codex

## Порядок

1. Прочитать `AGENTS.md` и текущую Issue `FOC-###` целиком.
2. Проверить раздел **Depends on**: заблокированные задачи не брать, даже если они кажутся интереснее.
3. Одна Issue = одна ветка = один PR. Для новых механик сначала уточнить компактный контракт/план, потом код.
4. Для Unreal-зависимых задач Codex обязан отличать **проверку исходников** от **реальной сборки и прогона UE** на Windows.
5. После PR владелец проверяет изменения, принимает/возвращает в доработку, сливает при готовности.

## Шаблон для Codex

```text
Работаем в репозитории Hazernit/fog-of-command.
Прочитай AGENTS.md, docs/ARCHITECTURE.md и docs/ROADMAP.md.

Выполни GitHub Issue #<НОМЕР> (FOC-###). Не начинай соседние Issues.
Сначала проверь зависимости и напиши короткий план изменения файлов и тестов.
Далее реализуй задачу в отдельной ветке, добавь релевантные тесты и открой PR.

Важно:
- WorldState и PerceivedWorldState не смешивать.
- Не пересоздавать подразделения при переключении управления.
- Не вводить глобальную экономику / PvP / магазин в MVP.
- Не сообщай, что Unreal собран и запущен, если фактически этого не проверял.
- В PR явно укажи: что сделано, как проверить на Windows, результаты тестов, что не проверено.
```

## Политика постоянных push и ранних Draft PR

При каждой работе Codex обязан **сохранять результат в удалённой рабочей ветке по ходу выполнения**, а не только отвечать отчётом в чате.

- Старт: проверить исходный репозиторий и ветку, получить актуальные `AGENTS.md` и связанную GitHub Issue.
- Первый полезный результат: атомарный `git commit`, `git push -u origin <issue-branch>`, открытие Draft PR с текущим статусом.
- Каждый следующий законченный шаг (скрипт, результат диагностики, тест, исправление): новый commit и push в эту же ветку; обновить описание PR и связанной Issue с результатами.
- Если шаг заблокирован (например, сборка Unreal FAIL): запушить безопасные документы/проверки, оставить PR Draft, приложить редактированную сводку (не raw-логи с приватными путями/токенами) и не писать `PASS`.
- Не использовать `main` как место для промежуточных коммитов, не запускать merge без владельца. Git LFS — для бинарных игровых ассетов, `.gitignore` — для временного и чувствительного.

### Windows FOC-046 после установки другого движка

Пользователь сообщил, что **установил новый Unreal Engine**. Это не доказывает исправление предыдущей сборки UE 5.3.2 с MSVC 14.51. Следующая работа на Windows должна:

1. Обнаружить **точную установленную новую UE версию** и путь, не предполагать, что это UE 5.8.4. Записать фактические MSVC и Windows SDK, которые выбирает UBT.
2. Повторить clean build **временного Blank C++ проекта вне репозитория** в новой версии UE; записать exit code, время, диагностические строки и выбранный toolchain. Ничего не устанавливать/не обновлять без согласования.
3. При успехе выполнить Editor/PIE smoke, затем проверить GPU (с учётом прежних сбоев Windows). При неуспехе сверить поддерживаемые инструментальные версии, рассмотреть уже установленный MSVC 14.44 вместо автоматического 14.51, **не** модифицируя движок без отдельного решения.
4. Результат оформить санитизированным `docs/diagnostics/FOC-046-windows-smoke.md` и сохранить **в той же feature-ветке через commit/push и Draft PR**. В Issue #53 и #7 сослаться на commit/PR, отметить FAIL/PASS/NOT RUN. Не переносить raw-логи и личные файлы в GitHub.
5. Не создавать `FogOfCommand.uproject` до FOC-002 и не закрывать #7/#53 без подтверждённой приёмки.

## Как заказывать несколько задач

Выбрать 2–3 задачи **без общих изменяемых файлов и без зависимостей друг от друга**. Не запускать в параллель FOC-004 (доменные типы) и FOC-016 (разведка) до стабилизации интерфейсов. Для игровых систем последовательные PR безопаснее автоматических многомодульных больших патчей.

**Сразу после публикации репозитория:** сначала FOC-001. Затем FOC-002. Только после них стоит передавать Codex задачи реализации UE-кода.

## Текущая очередь реализации (Windows baseline)

1. [FOC-001 / #7](https://github.com/Hazernit/fog-of-command/issues/7) — подготовить воспроизводимую процедуру и проверить выбранную версию/совместимость по документации. Текущий [Draft PR #52](https://github.com/Hazernit/fog-of-command/pull/52) не означает завершения Windows проверки.
2. [FOC-046 / #53](https://github.com/Hazernit/fog-of-command/issues/53) — реальная сборка пустого C++ UE-проекта, Editor/PIE и GPU smoke на Windows. Это **human-assisted gate**: Codex не может выдать PASS без Windows-логов.
3. После принятия #7 по результатам #53 можно отдельно запускать [FOC-002 / #8](https://github.com/Hazernit/fog-of-command/issues/8) — создать настоящий игровой `.uproject`.

**Правило передачи:** если задача частично зависит от ручного smoke, агент завершает доступную часть, открывает Draft PR с `NOT RUN`, перечисляет точные команды/артефакты и не блокирует разговор вопросом, если ответ не обязателен для документальной части. Не мержить и не закрывать зависимую Issue до приёмки.
